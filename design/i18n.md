# i18n — UI Multi-Language Support

Port the proven in-house pattern from `what-do-you-see` (`src/lib/i18n/translations.ts` + `src/hooks/useI18n.ts`, ~100 lines, no library). Decision 2026-09-21: initial languages **zh-TW (default) + en**; **ja + ko added 2026-09-26** (owner). Header top-right dropdown, instant switch.

## Three kinds of "language" — keep them separate

| Layer | What | Mechanism |
|-------|------|-----------|
| UI strings (buttons, statuses, errors) | zh-TW + en + ja + ko | i18n dictionary (this doc) |
| Translation language pairs (source/target pickers) | model capability list, grows over time | domain data table (`src/lib/`), **NOT i18n**; initial entries: `en`, `zh-TW` only — data-driven so adding a pair is a one-line entry |
| Model-facing instructions (chat template) | "translate … to …" | **always English** (AGENTS rule 8; what-do-you-see zh-instruction → tokenization-loop regression, 2026-09-21 rollback). Never routed through i18n |

## Files (port 1:1, keep single-file for a mechanical diff vs source)

- `src/lib/i18n/translations.ts`
  - `export type Language = "en" | "zh-TW" | "ja" | "ko"`
  - `export interface Messages { ... }` — flat dot-keys (93), ONE shared interface for all languages — a new locale missing any key is a compile error
  - `export const SUPPORTED_LANGUAGES: Array<{ id: Language; label: string }>` — the header picker renders straight from this list
  - `export const translations: Record<Language, Messages>`
  - `normalizeLanguage(value)` → unknown/missing falls back to `en`
  - `getMessages(language)`, `interpolate(template, vars)` (`{var}` substitution only)
- `src/hooks/useI18n.ts` — `const { t, lang, setLanguage } = useI18n()`; `setLanguage` writes settings → localStorage immediately (no Save step), so the header switch is instant

## UI

- MUI `Menu` in the header, top-right (same placement pattern as what-do-you-see); keyboard (Esc close, arrow navigation) is MUI built-in; `aria-haspopup="menu"` + i18n `aria-label` keys
- Language persists in settings (localStorage); default `zh-TW`
- Errors from `model-cache.ts` stay English (technical layer, no request context) — same policy as what-do-you-see; user-facing strings shown in the UI come from i18n keys

`src/lib/settings-manager.ts` reuses this module: `export type UILanguage = Language` and its `normalizeLanguage` delegates to the i18n one (2026-09-26). Before that it had its own hard-coded `"zh-TW" | "en"` + coercion — a ja/ko value in localStorage would have been silently coerced back to zh-TW. Never re-introduce a parallel language type there.

## Adding a language later (no mechanism change)

1. Add the value to the `Language` union
2. Add one entry to `SUPPORTED_LANGUAGES`
3. Add one dictionary to `translations` — the shared `Messages` interface makes any missing key a compile-time error

Refactors only when genuinely triggered:

| Trigger | Change | Cost |
|---------|--------|------|
| ≥10 languages (one file too fat) | split `translations.ts` → `locales/{en,zh-TW,…}.ts` + index export | file moves only; `useI18n` untouched |
| locale-aware dates/numbers | browser `Intl.DateTimeFormat`/`NumberFormat` with `lang` | no library |
| plurals | browser `Intl.PluralRules` | no library (UI barely needs them) |

## Acceptance criteria

- Switch in header → every UI string updates immediately, choice survives reload (localStorage)
- Add a dummy key missing from one dictionary → `tsc` fails (type safety holds)
- Model instructions in the network/console trace are always English regardless of UI language
